# 반도체 배관 CAD - 배관 태그 조회 해시테이블 (AutoLISP)

오늘 학습한 "해시 테이블의 충돌과 분포" 개념을 반도체 팹(Fab) 배관 도면 작업에
그대로 적용해본 예제입니다. AutoCAD/AutoLISP 환경에서 배관 P&ID 도면을 다룰 때
실제로 부딪히는 조회 성능 문제를 재현합니다.

## 상황

반도체 팹 배관 도면 한 장에는 보통 수천~수만 개의 배관 세그먼트가 있고,
각 세그먼트는 태그로 식별됩니다.

```
P-101-A-2FL   (Zone 101, 배관 A, 2층)
P-101-B-2FL   (Zone 101, 배관 B, 2층)
P-205-A-1FL   (Zone 205, 배관 A, 1층)
...
```

작업자가 도면에서 특정 배관 태그를 클릭하거나 스크립트로 일괄 처리(예: 특정
Zone의 모든 배관에 색상/레이어 일괄 변경, 간섭 체크, BOM 집계)할 때마다
"태그 → 엔티티(ename)" 조회가 반복적으로 발생합니다. 이 조회가 느리면 매크로
실행 시간이 도면 규모에 비례해 선형으로 늘어나 실무에서 체감됩니다.

## 나쁜 예 — [bad_linear_search.lsp](bad_linear_search.lsp)

가장 흔히 짜는 방식: `(assoc key alist)` 로 연상 리스트를 선형 탐색합니다.
배관이 200개일 때는 문제없지만, 20,000개가 되면 배관 하나 찾을 때마다 평균
10,000번 비교가 필요합니다. Zone 단위 일괄 작업(`getall-by-zone`)에서는
"전체 리스트를 매번 처음부터 끝까지" 순회하므로 문제가 더 커집니다.

또한 흔한 실수로, 해시를 쓰더라도 **Zone ID만으로 해시**를 만드는 경우를
같이 보여줍니다. 태그의 identity는 (Zone, PipeId, Floor) 세 개인데 hash가
Zone만 본다면, 같은 Zone에 배관이 많은 도면(실제로 흔함)에서는 특정 버킷에
몰려서 "해시테이블을 썼는데도" 사실상 선형 탐색과 다를 게 없어집니다.
→ 오늘 학습한 "hash는 ZoneId만 쓰는데 identity는 두 필드"와 동일한 함정입니다.

## 좋은 예 — [good_hash_lookup.lsp](good_hash_lookup.lsp)

배관 태그 전체(Zone+PipeId+Floor)를 문자열로 합쳐 해시 코드를 계산하고,
버킷 배열(AutoLISP에서는 리스트의 리스트로 흉내)에 분산 저장합니다.

- 같은 태그는 항상 같은 버킷으로 간다 (해시 일관성)
- 서로 다른 태그가 우연히 같은 버킷에 들어가도(충돌) equality 비교로 정확히
  가려낸다 (정확성은 항상 보장)
- 버킷 수를 배관 개수 대비 적절히 잡아 특정 버킷에 과도하게 몰리지 않게 한다
  (분포)

## 차이점 요약

| 항목 | 나쁜 예 (선형 탐색 / Zone만 hash) | 좋은 예 (복합키 hash) |
|---|---|---|
| 배관 1개 태그 조회 | O(N) — 도면 배관 수에 비례 | 평균 O(1) — 버킷 하나만 봄 |
| Zone 단위 일괄 처리 (도면당 Zone 20개, 배관 20,000개 가정) | 전체 리스트 20,000개를 매번 순회 | 조회 자체는 여전히 태그 단위 평균 O(1), 버킷이 균등하면 몰림 없음 |
| 도면 규모가 2배로 커질 때 | 매크로 실행 시간도 거의 2배 | 버킷 수를 같이 늘리면 실행 시간 거의 그대로 |
| 실무 체감 | "도면이 커질수록 매크로가 느려진다"는 불만이 나옴 | 도면 규모와 무관하게 일정한 응답 속도 |
| 흔한 함정 | Zone ID만으로 hash → 특정 Zone에 배관 몰리면 도로 선형 탐색 | Zone+PipeId+Floor 복합키로 hash → equality 계약 준수, 분포 균등 |

정확성(같은 태그면 같은 엔티티를 반환하는 것)은 두 방식 모두 지킵니다.
차이는 **조회 비용**입니다 — 도면이 커질수록, 그리고 매크로 안에서 조회가
반복될수록 이 차이가 누적되어 실제 작업 대기 시간으로 나타납니다.

## 실행 방법 (참고)

AutoCAD 명령창에서 순서대로 로드합니다.

```
(load "bad_linear_search.lsp")
(load "good_hash_lookup.lsp")
(load "bench.lsp")
```

이후 명령창에 `PIPE-BENCH` 를 입력하면 실제 팹 도면처럼 일부 Zone(101~104)에
배관이 몰리도록 더미 배관 태그를 생성하고, 다음 세 방식의 조회 비교 횟수와
버킷 분포를 함께 출력합니다.

1. 순수 선형 탐색 (alist)
2. Zone ID만으로 만든 hash (편중 발생 — 나쁜 예)
3. Zone+PipeId+Floor 복합키 hash (균등 분산 — 좋은 예)

실제 AutoCAD 엔티티 없이도 alist/해시 구조 자체의 비교 횟수 차이를
확인할 수 있도록 만들었으며, `*compare-count*` 전역 변수로 비교 연산
횟수를 계측합니다.

## C++ 재구현 & 발표자료

- [PipeTagLookup.cpp](PipeTagLookup.cpp) — 위 세 방식(선형 탐색 / Zone만 hash / 복합키 hash)을 표준 C++로 그대로 재구현한 버전. 컴파일해서 직접 실행하면 동일한 벤치마크를 재현할 수 있다.
- [PipeTagLookup_UE5.h](PipeTagLookup_UE5.h) — UE5 `TMap`으로 옮긴 실전 버전. 해시/버킷 구현을 엔진이 대신 처리한다.
- [PRESENTATION.md](PRESENTATION.md) — 개념·코드·실측 벤치마크 결과(선형/나쁜 hash 3,000회 vs 좋은 hash 22회, 약 136배 차이)를 발표용으로 정리한 문서.
