🚗 1️⃣  Context Switch = 자동차 운전자 교대
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

상황:
  자동차 1대 (CPU)
  운전자 1명이 10분씩 교대

교대 과정:
  1️⃣ 현재 운전자: "내 핸들 위치, 기어, 속도 메모해둬"
     → 손가락 위치, 시트 각도, 거울 각도 전부 저장
  
  2️⃣ 새 운전자 준비: "이전 운전자 설정으로 조정해"
     → 시트 조정, 거울 조정, 핸들 감도 재설정
  
  3️⃣ 주행 재개

문제점:
  ❌ 교대할 때마다 시간 낭비
  ❌ 차가 잠깐 멈춤 (context switch 비용)
  ❌ 새 운전자는 도로 상황을 모름 (캐시 비워짐)
     → 처음부터 다시 적응해야 함


시간대:
  0-10분: 운전자A 주행 (도로 잘 알고 있음)
  10분:   [교대 중... 잠깐 멈춤]
  10-20분: 운전자B 주행 (도로를 다시 학습)
  20분:   [또 교대 중...]


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🏪 2️⃣  Oversubscription = 손님이 직원보다 많음
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

상황 1️⃣ - 괜찮은 경우:
  식당 직원: 4명
  손님: 4명
  → 1:1 매칭, 모두 만족
  
  Timeline:
    점원1: [손님A] ──→ 끝
    점원2: [손님B] ──→ 끝
    점원3: [손님C] ──→ 끝
    점원4: [손님D] ──→ 끝
    
    총 걸린 시간: 1시간


상황 2️⃣ - 과포화 (Oversubscription):
  식당 직원: 4명
  손님: 30명
  → 점원 1명당 손님 7.5명... 무리!
  
  Timeline:
    점원1: [손님A(5분)] → [손님B(5분)] → [손님C(5분)] → ...
    점원2: [손님D(5분)] → [손님E(5분)] → [손님F(5분)] → ...
    점원3: [손님G(5분)] → [손님H(5분)] → [손님I(5분)] → ...
    점원4: [손님J(5분)] → [손님K(5분)] → [손님L(5분)] → ...
    
    [5분마다 고객 교대]
    [30명 처리하려면 30 × 5분 = 150분 = 2.5시간]
    
    문제:
    ❌ 자주 손님 바뀜 (context switch 증가)
    ❌ 점원이 손님 성향을 자주 까먹음 (캐시 초기화)
    ❌ 회전이 빠를수록 실수 늘어남
    ❌ 효율성 급락!

🔧 3️⃣  해결책 = 이미 알고 있는 것들
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🎯 전략 1: "할 수 있는 만큼만 고용"

❌ 나쁜 예:
  매 손님마다 새 점원 고용
  → 새 직원 교육 시간, 주민등록증 확인... (thread 생성 비용)
  → 10초 일 하고 해고 (thread 소멸)
  → 반복... 반복...

✅ 좋은 예:
  점원 4명만 고용 (CPU core 수)
  → 한 번만 교육
  → 30명 손님 처리
  → 점원들이 계속 일함 (no context switch!)
  
  코드:
  ```cpp
  TaskPool pool(4);  // 4명 고용
  
  for (int 손님 = 0; 손님 < 30; 손님++) {
      pool.Add일감([손님]() {
          ProcessGuest(손님);  // 처리
      });
  }
  // → 4명이 30명을 처리
  // → Thread 생성 비용 없음
  // → Context switch 거의 없음
  ```


🎯 전략 2: "I/O 대기는 다르게 처리"

상황: 손님이 "화장실 다녀올게, 5분만 기다려" 라고 함

❌ 나쁜 예 (Blocking):
  점원: "알겠습니다, 저도 여기서 기다릴게요"
  → 점원이 5분 동안 놀고만 있음 (다른 손님 못 봄)
  → 다른 3명 점원만 28명 손님 처리
  → 효율 급락
  
  코드:
  ```cpp
  while (손님이_화장실_중) {
      sleep_for(5초);  // 계속 확인
  }
  // → Thread가 blocking (capacity 낭비)
  ```

✅ 좋은 예 (Async/Callback):
  점원: "네, 돌아오시면 벨 눌러주세요"
  → 점원은 다른 손님 상대
  → 손님이 돌아오면 벨 울림
  → 점원이 다시 서빙 시작
  
  코드:
  ```cpp
  Async(
      [손님]() {
          손님.화장실();  // 5분 걸림
      },
      [손님]() {
          서빙계속(손님);  // 화장실 끝나면 호출
      }
  );
  // → Thread가 즉시 다른 일로
  // → I/O 동안 다른 일 가능
  ```

💻 4️⃣  코드로 보기 (초간단 버전)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

❌ 나쁜 코드 1: Thread 남발

```cpp
// 30개 작업, 매 작업마다 새 thread 생성
for (int i = 0; i < 30; ++i) {
    new thread([i]() {
        DoWork(i);  // 50ms 작업
    });
}
```

문제점:
- Thread 생성 비용: 30 × 1μs
- CPU 8개인데 30개 thread → 자주 교대 (context switch)
- 교대할 때마다 캐시 초기화됨
- 느림!


❌ 나쁜 코드 2: Blocking wait

```cpp
while (thread의개수 < 10) {
    new thread([&]() {
        DoWork();         // 30ms
        sleep_for(100ms); // I/O 대기 ← 여기서 문제!
        // 이 동안 thread는 뭐 하고 있나?
        // → 그냥 자고 있음 (capacity 낭비)
    });
}
```

문제점:
- 10개 thread가 100ms 동안 점유
- 다른 일이 있어도 못함
- 효율성 급락


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 좋은 코드 1: Worker Pool

```cpp
// 한 번만 4개 thread 만들기 (CPU core 수)
WorkerPool pool(4);

// 30개 작업 추가 (thread 생성 없음!)
for (int i = 0; i < 30; ++i) {
    pool.Add([i]() {
        DoWork(i);
    });
}

pool.Wait();  // 모두 끝날 때까지 대기
```

장점:
- Thread 생성: 4번만 (대신 30번이 아니라)
- Context switch: 거의 없음
- 캐시 계속 유지됨
- 빠름!


✅ 좋은 코드 2: Async (I/O 작업)

```cpp
// I/O 작업 + 콜백
Async(
    []() {
        // Worker thread에서 실행
        LoadAsset();  // 100ms (I/O)
        // ✅ 이 동안 thread는 다른 일 함!
    },
    []() {
        // Main thread에서 콜백
        ShowAsset();
    }
);
// ✅ 즉시 반환! Thread 블로킹 없음
```

장점:
- Thread가 I/O 대기 중에도 다른 일 처리
- Capacity 낭비 없음
- Game frame 안정적

🎮 6️⃣  게임 개발에서의 예
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

상황: 30개 적이 동시에 AI 계산 필요

❌ 나쁜 방식:
  매 적마다 새 thread:
  
  for (int i = 0; i < 30; ++i) {
      new thread([적들[i]]() {
          AI 계산();  // 50ms
      });
  }
  
  결과: 30개 thread, CPU 8개
  → 자주 교대 → frame drops ⚠️

✅ 좋은 방식:
  Worker pool 사용:
  
  for (int i = 0; i < 30; ++i) {
      taskPool.Add([적들[i]]() {
          AI 계산();
      });
  }
  
  결과: 8개 thread, 30개 task 분배
  → 부드러운 60fps ✓

🎓 7️⃣  정리 (초간단)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

📌 Context Switch
  = 자동차 운전자 교대할 때 시간 낭비
  = 매번 설정 재조정 필요 (캐시 초기화)
  → 자주 교대하면 느려짐

📌 Oversubscription
  = CPU 8개인데 thread 30개
  = 점원 4명이 손님 30명 담당
  → 자주 교대하니까 비효율
  → "사람 더 고용"은 도움 안 됨!

📌 해결책
  ✅ CPU-bound: 미리 thread 4개만 만들고 재사용
  ✅ I/O-bound: 대기 중에 다른 일 하기 (콜백)

📌 결과
  ❌ 무심코 30개 thread → 느림
  ✅ 4개 thread 재사용 → 빠름

Q: "Context switch가 뭐예요?"
A: "자동차 운전자를 교대할 때 시간이 걸리잖아요?
    CPU도 마찬가지예요. Thread를 자주 바꾸면 
    캐시가 초기화되고 느려져요."

Q: "Oversubscription이 뭐예요?"
A: "식당에 점원이 4명인데 손님이 30명이면,
    자주 교대하니까 비효율적이에요.
    이게 Oversubscription이고, 
    '사람을 더 고용하면 되지 않나?' 하면 더 느려져요."

Q: "그럼 어떻게 하는데요?"
A: "1. Thread 개수 = CPU 개수로 정해놓고 재사용해요
    2. I/O할 때는 대기하지 말고 콜백으로 다른 일 해요
    3. Unreal Insights로 Context switch 횟수 확인해요"
